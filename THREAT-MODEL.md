# Threat model

Observe holds credentials that can read most of the lab (SNMP v3 users,
a WinRM account, an MQTT account) and exposes an inventory of what is
monitored. Those are the assets. Each control below is labelled
**enforced** (the code or container prevents it) or **advisory** (it depends
on how you deploy).

## Trust boundaries

1. **Config and secrets to process.** YAML is mounted read-only; secrets come
   from environment variables or files under `/run/secrets`.
2. **Process to monitored devices.** Outbound SNMP, WinRM, MQTT, HTTP, DNS,
   ICMP, and TCP. Devices are treated as untrusted data sources.
3. **Dashboard to browser.** Inbound HTTP on 8080.
4. **Process to alert targets.** Outbound to ntfy, webhook, SMTP, MQTT.

## Controls

| Control | Status | Notes |
|---|---|---|
| No write endpoints for monitors, alerts, or credentials | enforced | Monitors, alerts, and credentials can only change by editing YAML and restarting. A dashboard compromise can read inventory, not mute alerts. The earlier blanket rule is superseded: the login, admin, and ingest surfaces below do write, and are listed separately. |
| Unresolved secret reference fails startup | enforced | Prevents silently running with an empty community or password. |
| Unknown config keys rejected | enforced | Typos such as `verfy_tls: false` fail loudly instead of being ignored. |
| Credential type must match monitor type | enforced | A WinRM secret can not be sent as an SNMP community by mistake. |
| TLS validation on by default (HTTP, TLS cert, WinRM, MQTT TLS) | enforced | Turning it off is an explicit per-monitor setting. |
| Device-supplied text rendered as text | enforced | `app.js` uses `textContent` only; CSP forbids inline script and third-party origins. `tests/test_ui_static.py` scans every HTML and JavaScript file under `observe/static` and the plugin `pages` and `static` folders and fails on inline script or style, `style=` and `on*=` attributes, the `innerHTML` family, `eval`, string timers, `element.style` and off-origin URLs, and asserts the CSP header on every page route, core and plugin. Covers hostile SNMP strings, MQTT payloads, HTTP error text. The theme choice (Auto, Light or Dark) is kept only in the browser's `localStorage` by `js/theme.js`, reads and writes are in try/catch, and nothing about it reaches the server or the CSP. The dashboard is an ES module that builds KPI tiles, status tiles and group cards from the same API with `textContent` only, which `tests/test_ui_dashboard.py` checks with a hostile monitor and group name. The shared chip, table, dialog and toast modules follow the same rules, render cell content only as Nodes or `textContent`, never put secrets in toasts, and are covered by the same scan plus `tests/test_ui_components.py`. Since slice S15 every page uses only same-origin stylesheets written with design tokens, so there is no legacy `app.css` and no inline style to audit. |
| Graph canvas | built, used by the map page | The force graph engine (`observe/static/js/graph/`, slice S9) paints device names and states to a `<canvas>` with `fillText`, so device-supplied text is never parsed as markup, and a static test bans markup-writing APIs and off-origin URLs in the files. It reads colours from CSS tokens, uses no inline style and no third-party code (the d3 libraries are not vendored). The layout is capped at 300 nodes and 360 steps, so a hostile or huge map payload cannot make the browser spin; above the cap the page falls back to the tiered view. The map page builds the side card with `textContent` only, and its links are same-origin port pages. Residual risk: a payload of 300 nodes still costs a few hundred milliseconds on a weak client. |
| PowerShell injection from config values | enforced | Values are embedded as single-quoted literals with quotes doubled; `disk` is pattern-validated. Tested in `test_windows.py`. |
| Secrets redacted from SNMP error text | enforced | Tested with a wrong community. |
| Container: non-root UID 10001, all capabilities dropped, read-only root, no-new-privileges | enforced by compose | Only if you run it with the provided compose file. |
| Unprivileged ICMP instead of CAP_NET_RAW | enforced by compose | Via the `net.ipv4.ping_group_range` sysctl, namespaced to the container. |
| Dashboard basic auth | advisory | Off unless configured. Constant-time comparison. By owner decision it opens only the read-only API and `/metrics`; it is never accepted for admin, user, ingest-key or future action routes, which need a session login with CSRF (tested against every admin route). Basic auth over plain HTTP is readable on the wire; put a TLS reverse proxy in front or bind to a management VLAN. |
| Dependency suppression can hide a real outage | advisory | A wrong `depends_on` (a server marked behind a switch it does not use) suppresses that server's alerts whenever the switch is down. Suppression is always recorded in the event log with the blocking monitor's name, and cycles and unknown parents are rejected at load. Review dependencies like firewall rules. |
| Database access confined to one layer | enforced | `observe/storage` is the only code that imports a database driver or opens a connection; `tests/test_storage_ban.py` fails the build on a violation. Reads run on connections opened read-only (`mode=ro` and `query_only`), so a read route cannot change data even through a bug, and a read that runs past 2 seconds is interrupted. Every write is one transaction on a single writer, and `foreign_keys` is now enforced. |
| Network exposure of 8080 | advisory | Compose publishes on all interfaces by default; bind to one address if needed. |

## Ingest, logins, and control

These rows describe the hostwatch ingest and login work in
`docs/ARCHITECTURE.md`. **planned** means the design is decided and the
control is not yet verified.
The owner reversed the earlier read-only-by-design decision, so these
surfaces write.

| Control | Status | Notes |
|---|---|---|
| Ingest keys bound to one host | built, used by `POST /api/ingest` | A key is valid only for the host name it was created for, shown once, stored as a SHA-256 digest of 256 random bits, and revocable. Verification compares in constant time, treats an unknown key like a wrong one, and records last use only on success. The endpoint answers 401 for a bad or revoked key and 403 for a good key presented for another host, and stores nothing in either case. The `wpi_` marker is the host ingest scope, and no other surface accepts these keys. Keys carry a scope that is checked twice, from the marker and from the stored `scope` column, so a `wpf` field report key is refused by host ingest and a `wpi` key is refused for field reports, and editing a marker does not change a key's scope. Only `wpi` and the scopes of listed plugins can be issued, and the create is audited with the scope. For a plugin scope the bound name is a device label, and a revoked key fails like a wrong one. The Pockethernet report schema rejects unknown fields, SSH transcripts and script values (by name, at any depth), properties outside an allowlist, and non-finite numbers, and caps body size, nesting, strings and lists, so a stolen `wpf` key cannot push arbitrary structure or a secret-bearing transcript into the database. Location and Wi-Fi fields are accepted by owner decision and stay with the report; they never become port properties. A stolen key can impersonate only its own host. Keys are created and revoked from the admin screen (`/admin`, admin session and CSRF) or the command line. The new key appears once, in the create response, which is sent with `Cache-Control: no-store`; the key list never contains a secret. |
| Dashboard layout is per user | built | `GET`, `PUT` and `DELETE /api/ui/layout/{view}` use the session's own user id, never one from the request, so a user reads and writes only their own row. `PUT` and `DELETE` need the CSRF token, basic auth is never accepted, only the view `dashboard` exists, ids must match a fixed shape, lists are capped at 200 entries and the body at 32 KiB. A layout holds tile names only, which are shown as text. Residual risk: a signed-in user can store up to 200 group-name strings of their own, which no one else reads. |
| Ingest input validated | built | The endpoint reads no body until the key is valid, caps the body at 1 MiB, and validates against the wire models, which ignore unknown fields, reject unknown schema versions and cap list sizes, string lengths and event detail. A failed request stores nothing. A boot kind the server does not recognise is classified unknown, never clean. Replay is idempotent, by `batch_id` or by a content hash when none is sent. Residual risk: a holder of a valid key can still report false readings or false boot events for its own host. |
| Ingest rate limit and denial logging | built | A fixed-window limit per peer address (`server.ingest_rate_per_minute`, default 120) returns 429. Denied requests are audited at most once per peer per minute with a count, and at most 4096 peers are tracked, so a scanner cannot grow the database or memory without bound. The peer is the socket address, so behind a reverse proxy every client shares one bucket; put the limit in the proxy as well. The audit row holds the key's public prefix, never the key. |
| Unconfirmed pushed hosts never alert | planned | A new host stays pending until an admin confirms it, so an unknown sender cannot create alerts. |
| Sessions | built | Passwords are Argon2id hashes (argon2-cffi). A login makes a 256-bit random session identifier, stored only as a SHA-256 digest, sent in an HttpOnly, Secure, SameSite=Strict cookie. Sessions end at an idle limit (`session_idle_s`, 30 minutes) and an absolute limit (`session_absolute_s`, 12 hours), and a session is revoked once seen expired, on logout, or when its user is disabled. An unknown, locked or disabled account costs one dummy hash check and gets the same 401 body as a wrong password. An account locks after `login_max_failures` failures for `login_lock_s`, and a correct password does not unlock it early. Logins are also limited per peer (`login_rate_per_minute`), and failures are audited at most once per peer per minute. Residual risks: the lock lets someone who knows a username keep that account locked out; the peer is the socket address, so behind a proxy every client shares one bucket; `session_cookie_secure` can be turned off for plain HTTP, which exposes the cookie on the wire. |
| Series storage and compaction | built | Readings are stored as series under a resource named by the authenticated host, so a `wpi` key still writes only its bound host's resource (the binding is checked before `record_points` runs, and the resource is made from the batch host). A hostile or buggy agent cannot grow the database without bound by inventing label sets: at most 2,000 series per resource and 50,000 in all are created, and points for a series over a cap are dropped and counted; labels were already limited in number and length by the wire schema. A point is keyed by series and millisecond, so a replayed batch cannot add rows or change a summary, and an out-of-order point cannot overwrite a newer latest value; a key holder can still resend a point with a new value for the same millisecond, which replaces the stored value and corrects the summaries, so the newest write wins for that point. The summary levels are built in the ingest transaction, and compaction removes raw or summary rows only after checking that the level above still counts them, so a failed or interrupted summary cannot lead to silent data loss; a series that fails the check is kept and the failure is shown on the admin retention page. Deletes run in chunks of at most 5,000 rows, so a long compaction cannot starve ingest. Removing a host deletes its resource, series, samples and summary rows in the same transaction as its keys and enrolment. The read views expose the small summary tables only and never raw samples. Residual risk: on TimescaleDB the aggregates are trimmed by policy rather than per series, so a removed host's summary buckets stay until retention (they are hidden from the views), raw chunks can outlive the raw level by up to a day, and the coverage check is a count comparison, so it detects missing summaries but not a wrong sum. |
| Re-check settings | built | `GET` and `PUT /api/admin/recheck` and the page `/admin/recheck` need an admin session, and the PUT needs the CSRF token; basic auth and ingest keys are refused and a non-admin gets 403. Values must be numbers inside fixed bounds (window 0 to 86,400 s, interval 5 to 3,600 s, 1 to 20 good replies), unknown names are refused and an override must name a configured monitor, so a request cannot set a zero interval that would hammer a host. Each change writes one `recheck_settings_changed` audit row with the old and new values in the same transaction; a refused request is audited as `recheck_settings_failed`. The page is written with every value HTML escaped. Residual risk: a compromised admin can turn the re-check off for a monitor (window 0) or lengthen it, which delays a Down alert; the audit row records it. |
| Retention settings | built | `GET` and `PUT /api/admin/retention` need an admin session, and the PUT needs the CSRF token; basic auth and ingest keys of any scope are refused (401), a non-admin is refused (403). Values must be whole numbers inside fixed bounds, unknown names are refused, and at most 100 metric overrides are kept, so a request cannot set an unbounded or zero retention. Each change writes one `retention_settings_changed` audit row with the old and new values in the same transaction; a refused request is audited as `retention_settings_failed`. Residual risk: a compromised admin can shorten retention and so cause earlier deletion of history, which the audit row records but cannot undo. |
| CSRF protection | built | The token is an HMAC of the session identifier, so it exists only for the holder of the session and a leaked database does not reveal it. Every state-changing route that needs a session (`/api/logout`, `/api/admin/*`) requires it in `X-CSRF-Token`, compared in constant time, in addition to SameSite=Strict. A token from another session is refused. Residual risk: `POST /api/login` has no token because there is no session yet; SameSite=Strict and the JSON-only body limit login CSRF, and the worst case is signing a victim in as the attacker. |
| Admin role | built, minimal surface | `users.is_admin` is read from the database on every request, never from the cookie. The admin routes (`/api/admin/users`, user disable and role, and `/api/admin/keys` with revoke) all use the same dependencies; confirmation and future action routes will too. A non-admin gets 403, no session gets 401, and the tests drive every admin POST without a token. The last active admin cannot be disabled or demoted: the check and the change are one SQL statement, so two requests cannot both remove it. Disabling a user ends their sessions on the next request. An admin can still grant admin to another account, so the admin role is as sensitive as the database. The first admin is created from the command line with `--create-admin`, which reads the password from `OBSERVE_ADMIN_PASSWORD` or a prompt and never from an argument. |
| Pushed hosts as confirmed monitors | built | A host is a monitor only when it is listed in the YAML, so a valid ingest key alone cannot add a monitor or page anyone. Its status goes through the same confirmation counts as every other monitor, so one bad batch does not page. Silence is treated as failure: no batch within `stale_after` fails the check, so a host that stops pushing, or a key holder who stops reporting, shows as down. Residual risk: a key holder can report healthy readings for its own host and keep it green, and can report false Critical readings to page. The key limits that to one host. Only the YAML sets component thresholds, never the agent. |
| SNMP host readings | built | An `snmp` monitor with `host_name` writes its readings into the store through `Store.ingest_batch` in process, like HA host mode, so the ingest key check is bypassed on purpose and the host name comes from the YAML only. Values come from numeric SNMP replies and are parsed as integers; a malformed row is skipped, a mount description is truncated to 1024 characters and written with `textContent`. Nothing new is sent to the agent: the storage mode only adds GET and walk requests for the HOST-RESOURCES tables the check already reads, using the same credential and redaction. Residual risk: whoever controls the SNMP agent controls those readings, and a monitor given the host name of a pushed host writes beside that host's own series, so choose a name no agent pushes under. |
| Home Assistant host mode | built | Reads `/api/config` and `/api/states` with the existing non-admin token, GET only, no redirects followed, and each reply capped at 16 MiB, so a hostile or broken HA cannot exhaust memory. Observe holds no HA admin token. The readings enter the store through `Store.ingest_batch` in process, bypassing the ingest key check on purpose, and are bound to the monitor's `host_name`. Entity names and states from HA are written into sample labels, truncated to 1024 characters, and the page writes them with `textContent`. Residual risk: whoever controls HA states controls those readings, and ha_Int_soc may push to the same host under its own source names with a key bound to that host, so its readings sit beside these and a key holder can overwrite the same series. |
| Home Assistant push from HA SOC | built | ha_Int_soc posts hostwatch batches to the ordinary ingest route with a `wpi` key bound to `homeassistant`, so the key cannot write any other host, and the usual body, count, depth, rate and replay limits apply. Observe holds no HA admin token. A push key holder can write any series of that host and its events, including crash classifications, and can overwrite the pulled readings of the same series, so the key belongs only in HA SOC. Labels and titles are written with `textContent`. `boot.core_restart` is deliberately never a clean shutdown. Residual risk: the pushed names are a proposed contract that is unverified against a live HA SOC. |
| Classic UniFi controller credential | built, optional | The `unifi_classic` account is a dedicated local view-only user, so a stolen password reads the console but changes nothing, provided the account really is view-only, which Observe cannot check. The client sends only the login and logout POSTs and GETs of four read views, a spy test fails on any other method or path, the session cookie and CSRF token live in memory only, and no redirect is followed. The password is in the config environment like every other secret. Residual risk: a console admin who grants the account more rights widens the damage, and the password is in process memory. |
| Client privacy | built | `unifi_clients` and `unifi_cameras` hold who is on the network, where they plug in, their SSID and the names they chose, so the database is a presence map. Rows are deleted after 30 days unseen, the routes need a login session, and every name is written with `textContent`. Residual risk: anyone with database or session access sees device names and times of presence, so treat a backup as personal data. |
| HA SOC push key | built | The `wpi` key for `homeassistant` lives only in HA SOC, is bound to that host so it cannot write any other, and is limited by the ordinary ingest body, rate and replay checks. Residual risk: a leaked key lets its holder write that host's series and events until the key is regenerated. |
| Audit log | partly built | Rejected ingest (`ingest_denied`), `login_ok`, `login_failed`, `logout`, `user_created`, `key_created`, `key_revoked`, `user_disabled`, `user_enabled`, `user_promoted` and `user_demoted` are written now, plus a `*_failed` or `*_error` row when an action stops partway (`login_error`, `user_create_failed`, `user_create_error`, `key_create_failed`, `key_revoke_failed`, `user_change_failed`, `user_change_error`, `ingest_failed`). Every row goes through `audit.record`, which sanitizes the path and redacts detail fields named like secrets; passwords, tokens, keys and attempted passwords are never written, and a failed login records the account name only when the account exists. `GET /api/audit` is admin only and needs a session, so basic auth cannot read it. The retention page `/admin/retention` needs an admin session (401 and 403 otherwise), is written with every value HTML escaped, carries the CSRF token that the settings `PUT` still checks, and shows the backend name only: the DSN and its password are never rendered, and a stored maintenance error is cut to 200 characters. The audit page `/audit` is a static file with no data, filters in the browser, writes every row with `textContent`, and a viewer who opens it gets 403 from the API and an "admin account needed" notice; hiding the nav entry from viewers is tidiness only. Confirmations are planned, because no route exists for them yet. Changes made on the admin screen are recorded with the signed-in admin as actor. Changes made with the command line are recorded with the actor `cli`, which proves only that someone had shell access. The redaction is name based, so a caller that put a secret under an innocent field name would still leak it; the tests check each writer. Append-only from the application's side. Anyone who can edit the database file can still alter it, so protect `./data`. |
| PostgreSQL connection secret | built | With `storage.backend: postgres` the connection string must not contain a password (a string with one is refused at load, and the error does not repeat it); the password is read from `storage.password_file`, as for other secret files, and handed to the driver separately. The string and password are scrubbed from storage errors, from the pool's log records and from reprs, a failed connection raises an error without the driver's own message chained in, and a configuration error replaces the string with a marker. `docker-compose.yml` publishes no port for the database, so only the Observe container reaches it, and the password is a file in `./secrets`. Residual risk: the database host name and user name are not secret and can appear in the driver's connection error text; a backup of the PostgreSQL volume is plaintext history like the SQLite file; the CI workflow uses a throwaway password for an ephemeral service container only. The read pool opens repeatable-read read-only transactions, so a read route cannot change data on either backend. |
| Versioned store | built, partly used | Migrations are additive, guarded, and transactional per step. A database written by a newer version is refused rather than opened. The audit table has its own retention, `server.audit_retention_days`, separate from poll retention. Host data, ingest keys, batch ids and rejected-ingest audit rows are written now; users, sessions and login audit rows are written by the login routes. Expired sessions are pruned with poll retention. |
| Per-host hardware views | built | `GET /api/hosts`, `GET /api/hosts/{host}` and the `/host` page are read-only. The two API routes need a login session, and basic auth does not open them, because they expose hardware inventory, disk serials and boot history. The `/host` page itself is a static file with no data, like `/login`, and sends a visitor without a session to the login page. Agent text (labels, reasons, event titles) is written with `textContent` only, so hostile text renders as text under the existing CSP. A stale, failed or missing source is labelled as such and never shown as healthy or as zero, so a key holder cannot hide a silent host by sending nothing; a key holder can still send false readings for its own host. Residual risk: a host that is not listed in the YAML still appears here, marked as not monitored, so a valid key reveals that host name to every logged-in user. |
| Control plugin keys and signing | partly built | The `control` plugin (docs/CONTROL.md) owns the `wpc` key scope, a key bound to one host name. The core checks the marker and the stored scope together, so a `wpc` key is refused by host ingest and field reports, and `wpi` and `wpf` keys are refused by `GET /api/v1/control/commands`, with tests for each, including keys whose marker was swapped. The route returns 403 when a valid key asks for another host, and no commands exist yet, so a stolen host key can pull nothing. Commands are signed with an Ed25519 key loaded from a PKCS8 PEM file; on POSIX the plugin refuses to start if the file is readable by group or others, missing, or not an Ed25519 key, and error messages never include key material. `--control-keygen` writes the file with mode 0600, never overwrites, and prints only the public key. The signature covers canonical JSON (sorted keys, no spaces, UTF-8), and a fixed test vector in docs/CONTROL.md and the tests pins the format; changing any field fails verification. Residual risk: the private key is an unencrypted file, so anyone who can read it as the Observe user can sign commands, which are still bounded by each host's own allowlist; on Windows the permission check is not enforced, so protect the file with an ACL. The command queue, pull and results routes are built (slice `ctl-queue-pull`). Pull selects rows by the key's own host only, so a stolen host key sees only that host's unexpired, unfinished commands, and a `wpc` key asking for another host gets 403. A result is accepted only for a command of the key's host: an unknown id and another host's id both get the same 404, and are audited with the reason, so ids cannot be probed or another host's command closed. Results are final once (409), output is redacted of key-shaped text and cut to 4096 characters before storage, the body is capped at 256 KiB, and a command that expires without a result becomes `unknown`, and a late result cannot make it `done`. `seq` is assigned per host inside the same transaction as the rate limit checks (one pending per host and action, 10 per host per hour, one reboot per 15 minutes), so concurrent requests cannot pass them together or reuse a seq. The audit log gets `control_requested`, `control_request_refused`, `control_pull` (first delivery only, so an idle poll writes nothing), `control_expired` and, through the plugin audit middleware, a `plugin_request` row for every result with its outcome. Residual risk: a result is trusted as reported by the host, so a compromised host key can claim any outcome for its own commands; an `unknown` or late-result command may still have run on the host; redaction is pattern based (key prefixes, bearer values, Authorization lines, PEM blocks, assigned secrets and runs of 32 or more base64 or hex characters, applied before truncation). Header and service names are matched in full and `confirmed` must be the JSON boolean true. The admin request routes, confirmation, cancel and the host page Control section are built (slice `ctl-ui`). The routes need an admin session and the CSRF token, so a non-admin or a forged cross-site request gets 403 and creates nothing. Every request needs an explicit confirmation, a reboot needs the host name typed exactly, parameters are checked against a strict per-action shape and, when known, the host's reported fan headers, and the queue's rate limits still apply. A cancel changes only a `requested` or `scheduled` command, with one guarded update, so a result arriving at the same moment cannot be overwritten. A result is accepted only for a command the host has pulled, and `scheduled` only for `host.reboot`, so a host cannot answer a command it never saw. `confirm_host` stays in the admin request body and is never part of the signed params. Refusals and cancels are audited, and the page writes every host-supplied or result string with `textContent`, with a test that bans markup-writing APIs in its script. The host page and its Control card are ES modules under the same strict CSP (slice S6); the confirmation and typed-name dialog are the shared `dialog.js`, a refusal appears as an inline notice and a toast built from the server's `detail` text only, and the server still re-checks `confirmed` and `confirm_host`, so the dialog stays a convenience and not the gate. Residual risk: an admin session that passes the dialog can still request any allowed action, bounded by rate limits and each host's allowlist; the daemon learns of a cancel of a scheduled reboot from the `cancel` list in the pull response, kept until the host acknowledges it (at most seven days), so a cancel made after the host has already rebooted has no effect, and the host then reports `done` so the record stays true. |
| Host enrolment | built (API and the Linux, Raspberry Pi, TrueNAS and Windows scripts) | `POST /api/hosts` and `GET /api/hosts/{name}/enrolment` need an admin session, and the POST needs the CSRF token; basic auth never opens them. The install token (`wpe_` plus 256 random bits) is shown once in the create response, which is `no-store`. Only its SHA-256 digest is stored. It lasts 30 minutes, is claimed by one conditional `UPDATE` so it works once, and is not placed in any query string, audit row, progress response or log line; the audit redactor treats `wpe_`, `wpc_` and `wpi_` text and any 40-character run as secret. The agent and control keys do not exist until the token is redeemed, so an expired or unused token leaves nothing to revoke, and each key is bound to the one host name. Allowlist entries are matched against the control daemon's own character sets, so a hostile entry cannot carry shell syntax into a later generated config or sudoers rule. The command text names the host and platform in its first line so it is not run on the wrong machine; the Linux and Raspberry Pi script also refuses to run unless it is root, the hostname (short or fully qualified, any case) is the enrolled name, and the machine is not the Observe host (machine-id and address comparison), all before it changes anything, and each refusal is reported to Observe. `GET /i/{token}` needs no session, is rate limited per peer, serves a script that holds no key and does not spend the token, and answers 410 for a used, expired or unknown token; every value in the script is validated server side and single quoted. The script spends the token only after its guards pass, by posting it to `POST /api/enrol/redeem` (token on curl's standard input, never a command line), which claims the row with one conditional `UPDATE` and returns the keys as `no-store` JSON that the script reads with `sed` and never evaluates. A guard that refuses reports to `POST /api/enrol/guard`; the route needs a live token, keeps only a fixed-text reason (the machine's own name is cut to host name characters and 64 of them), and leaves the token valid. The address in a command and in a script is never the request's Host header, which the sender controls: it is `server.public_url`, or an address an admin confirmed and saved, validated as `http(s)://host[:port]` with no path or shell metacharacters and never a loopback or wildcard name, so a forged Host header cannot point a pasted command at another server, and the address is validated again before it is written into a script. With no address, commands are refused (409) before a token is made or a key revoked. Keys are written to files with root-only modes (`agent.env` 0600; `control.toml` and `control.env` 0640 for the control account), never echoed, never put on a command line, and never sent in a progress report. The reports are authenticated by a separate step key (`wps_`, digest only, two hours), whose notes are redacted and capped. The sudoers file is checked with `visudo -c` before it is installed. The TrueNAS shell script and the Windows PowerShell script (agent only) apply the same three guards before any change; the TrueNAS script writes `agent.env` 0400 on the pool and a compose file that holds no key, and the Windows script hands the key to hostwatch's installer as a SecureString object, so it is on no command line and in no transcript, and removes its temporary download folder. The TrueNAS `pool` and every other value is validated and quoted (single quotes, doubled in PowerShell), and the script text is ASCII. Control is refused for both platforms. Residual risk: the Windows script downloads hostwatch's `main` branch archive over HTTPS and runs its installer as administrator, so it trusts that repository and GitHub; nothing pins a commit. Residual risk: whoever holds the token can read the keyless script and call the guard route to overwrite the stored refusal reason, which only shows text to the admin; the Observe-host guard cannot compare a machine-id when Observe runs in a container that hides it, and then relies on addresses. Residual risk: whoever sees the command in the console, a terminal history or a chat can use it within 30 minutes if the admin has not. ## Re-check probes

The fast re-check of a pushed host (docs/DATA-API-DESIGN.md section 10.3) makes Observe send one
ICMP echo, or open one TCP connection, every `recheck_interval` seconds (at least 5) for at most
`recheck_window` seconds, to the host's `address` or name and `recheck_port`. Both values come from
the YAML that an administrator controls, never from an ingest batch, so a pushing agent cannot
aim these probes at another address. The probes stop when the host goes Down, so a dead host is not
probed at the fast rate, and a re-check of a child does not start while its parent is Down. Degraded
notices go only to alert targets that opt in, so a flapping link cannot fill a channel by default.
A pushed host that answers ping while its agent is silent reads as recovered; the host stays
visible as Degraded and Up in the event history, and its data goes stale on the host page.

## Discovery

Discovery sends credentials to addresses it has not seen before, which is a
different risk from polling known hosts. Controls:

## Accepted risks

**SNMP secrets in process arguments.** The net-snmp tools take the community
or v3 passphrases as argv, readable from `/proc/<pid>/cmdline` for the life of
each poll by anything in the same PID namespace. The container runs only
Observe, and host root can already read the container's environment and
memory, so this does not add an attacker class. Reconsider if you run other
processes in the container.

**Secrets in memory and environment.** Resolved secrets live in the process
for its lifetime. Use `${file:...}` references to keep them out of
`docker inspect` output, which shows environment variables.

**Kerberos keytab is a long-lived bearer secret.** A keytab lets its holder
authenticate as the account indefinitely, until the account's password is
rotated (which invalidates every keytab derived from it, unlike a leaked
password that can be changed while other holders keep working from other
credentials). It never touches `${ENV}`/`docker inspect`: `keytab_path`
points at a file under `./secrets`, read directly by `kinit`. The acquired
ticket is cached in the container's `/tmp` tmpfs, so it does not survive a
restart and is never written to the read-only root filesystem or to `./data`.
Treat the keytab file itself exactly like a private key: readable only by
the account that runs Observe, and rotated (regenerate with `ktpass`, no
disable/re-enable of the account needed) on the same schedule you'd rotate a
WinRM password.

**Database history is plaintext.** SQLite (`./data`) or PostgreSQL (the `observe-pgdata`
volume) holds hostnames, check messages, and values, not credentials. Protect it like the
config, and keep the PostgreSQL password file under `./secrets`, not in the config.

**Alert payloads leave the lab.** A public ntfy topic or webhook receives
monitor names and messages. Use a self-hosted or authenticated target if that
matters.

## Least privilege for monitoring accounts (advisory)

- SNMP: a v3 user with a read-only view scoped to the MIB subtrees you poll.
- WinRM: a dedicated domain account, not an administrator, granted remote
  management access and CIM read rights on the target classes, and denied
  interactive logon. Certificate mapping removes the password entirely; so
  does Kerberos (`transport: kerberos`), at the cost of holding a keytab
  instead (see "Kerberos keytab is a long-lived bearer secret" above). Not a
  gMSA: gMSA passwords are retrievable only by domain-joined Windows
  computer accounts, which a container is not.
- MQTT: an account with ACLs limited to subscribing to the topics you check
  and publishing under the alert `topic_prefix`.

## UniFi ports mode

The `ports` mode of `unifi_network` sends only GET requests with the existing API key. It does not follow redirects, so a hostile or misconfigured console cannot send the key to another host, and it refuses a device detail body larger than 1 MB so a response cannot exhaust memory.

## UniFi plugin

The `unifi` plugin reads the Integration API with the key of a `unifi` credential. It sends only GET requests, never follows a redirect so the key cannot be forwarded to another host, caps each response at 4 MB and a list at 50 pages, and never writes the key to the database, a log line or an error message. After a 401 or 403 it backs off, doubling its pause up to one hour, so a revoked key is not retried every interval. A device row holds names, MAC and IP addresses and firmware versions, so the database is as sensitive as the inventory already in it. Records unseen for 30 days are deleted. The optional `unifi_classic` credential is a dedicated local view-only account used by the classic client (`classic.py`). That client sends only `POST /api/auth/login`, `POST /api/auth/logout` and GETs of `stat/device`, `stat/sta`, `rest/user` and `stat/health` under `/proxy/network/api/s/{site}`, and a test with a transport spy fails if any other method or path is sent. The session cookie and CSRF token stay in memory, never in the database, a log line or an error message, and the password is never logged. A 401 causes one re-login and one retry, then a back-off that doubles up to one hour. Redirects are not followed and a response is capped at 8 MB. The classic site name is limited to letters, digits, underscore and hyphen so it cannot alter the path. The account should be view-only: Observe cannot enforce that, so a stronger account widens what a stolen password could do. The map feed adds no network access: it writes what those reads returned through the infrastructure service, and a test checks that after the login only GETs are sent. It stores device names, MAC and IP addresses, port numbers, VLAN ids and PoE watts in the map tables, so the database holds a wiring and VLAN plan. A device or neighbour MAC can be forged on the network, so `lldp` links and neighbours are limited to devices the console already lists or the map already knows, and nothing the feed writes creates or changes a monitor. The plugin runs in process with the full trust described under Plugin host above.

The clients collector adds no network access beyond the same GETs: it reads the Integration client list and, with the classic account, `stat/sta` and `rest/user` through the same client, and a test fails if anything but the login POST and GETs is sent. The Protect collector sends only GET `/cameras` with the same key, no paging parameters, no redirects, and has its own backoff after a 401 or 403. `unifi_clients` holds the name, MAC and IP address of every device on the network, with its switch port and SSID, so the database is a map of who is on the network and where; rows are deleted after 30 days unseen. A client chooses its own name, so every name, SSID and camera name is untrusted text: the routes return it as JSON with `nosniff` and the UniFi page writes it with `textContent` only, which tests check with hostile strings and the static guard. The page routes need a login session, and the page itself holds no data. The classic note shown on the page is built from error classes and status codes, never from a credential.
